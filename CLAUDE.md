# AI Chat Platform

Multi-tenant AI customer-support chatbot SaaS. A "mother" dashboard for the platform team manages every client business; each client gets its own dashboard scoped to their data. The Hermes agent engine answers customer questions through per-client Hermes agent profiles (each profile carries its own model/config), hands off to a human when it can't help, and connects to the customer's website, Facebook Messenger, Instagram, and WhatsApp.

## Stack

- Turborepo + pnpm monorepo. `apps/web` is the only app — Next.js 16 (App Router), Node ≥18.
- Postgres via Prisma (`packages/database/prisma/schema.prisma`) — production runs its own local Postgres on the VPS (see Deployment below); this laptop's local Postgres (`DATABASE_URL`/`DIRECT_URL` in `.env` and `apps/web/.env.local`) is a separate dev-only instance, not the same database as production anymore.
- ~35 single-purpose packages under `packages/`, wired together through one composition root.

Root commands: `pnpm dev` / `pnpm build` / `pnpm lint` / `pnpm check-types` (all `turbo run ...` across the workspace). `apps/web` also has its own `next dev`/`next build`/`eslint --max-warnings 0`.

## Architecture

**Composition root, not DI framework.** `packages/bootstrap/src/container.ts` (`Container`) constructs every service and controller by hand and wires them into one `ApiRouter`. `packages/bootstrap/src/create-app.ts` builds the `Container` with real providers (AI keys, embedding keys, vector store). `apps/web/lib/app.ts`'s `getApp()` memoizes one `Application` instance on `globalThis` per server process. Every API route calls `getApp()` then `app.container.router.<controller>.<method>(...)` — no route talks to Prisma or a package directly.

**Packages are single-purpose and layered**: `hermes` (OpenAI-compatible client that talks to the local Hermes gateway; per-tenant API keys live in `<HERMES_HOME>/profiles/<slug>/.env`) → `chat-service` (the single chat pipeline: business gating, prompt, booking bridge, handoff logic) → `api` controllers → `apps/web` routes. Channels are `channel-catalog` adapters (`web`, `messenger`, `instagram`, `whatsapp`) with `channel-connections` persistence. Hermes is the **only** AI engine in the codebase — the legacy multi-provider retrieval stack (`ai-manager`, `provider-catalog`, `rag`, `embedding-*`, `vector-store`, `knowledge-refresh`, `openrouter`) was deliberately removed.

**Two dashboards, shared components.** `apps/web/app/dashboard/page.tsx` (mother, platform-wide) and `apps/web/app/dashboard/[businessId]/page.tsx` (per-client) render mostly the *same* components (`HermesAgentsPanel`, `AllChatsPanel`, `ContactsPanel`, `InvoicesPanel`, `ReportsPanel`, upstream business panels like `TeamChatPanel`, `WhatsAppTemplatesPanel`, `PurchaseOrdersPanel`, `ShiftsPanel`, `LocationsPanel`, etc.) — an optional `businessId` prop switches between platform-default and client-scoped behavior. Prefer extending a shared component over forking one per dashboard.

**Per-business flags, read fresh per message.** There is no versioned config table. `ChatService.chat()` reads one `Business` row fresh on every message: `aiEnabled` (master AI on/off), `hermesEnabled` + `hermesProfile` (which Hermes agent answers), `languageMode`, `timezone`. A dashboard toggle takes effect on the very next customer message, no restart.

**Multi-channel messages funnel through one pipeline.** A webhook-received Messenger/Instagram/WhatsApp message and a website-widget message both end up calling `ChatService.chat()` — same Hermes engine, same handoff logic. `Conversation.channel` records which channel it came from; `Conversation.externalUserId` is where a human agent's reply gets sent back out through that channel's own Send API (see `HandoffController.reply`).

**Hermes agent engine (the branded AI is AIVA; Hermes is the engine — and the only AI in the codebase).** In one decision point `ChatService.chat()` routes a conversation to the Hermes engine for any business with `hermesEnabled` + a provisioned `hermesProfile`; businesses without a profile fall through to the platform default profile (`DEFAULT_TENANT`, "aiva-portal"). The route covers every channel (widget, Messenger, Instagram, WhatsApp). The agent's `[[BOOKED:{...}]]` marker is bridged to a real `Order`/`RepairAppointment` row (with the default `Location` attached), `[[NEEDS_HUMAN]]` to a real conversation handoff; the human/AI gates still apply (AI off, or a conversation already with a person, gets the canned waiting reply). Engine pieces: `packages/hermes` (OpenAI-compatible client; reads the tenant API key from `<HERMES_HOME>/profiles/<slug>/.env`), local gateway at `127.0.0.1:8642` via `scripts/hermes/serve-dev.mjs` (needs `HERMES_HOME=<repo>/data/hermes` and `HERMES_GUEST_ONBOARDING=1`), profiles provisioned via `scripts/hermes/provision-agent.mjs` (writes `Business.hermesProfile`; it never flips `hermesEnabled` — that's a per-client switch in the mother dashboard's Client Access panel, alongside the AI Replies switch). Stable conversation memory rides on the `X-Hermes-Session-Key` header (`${businessId}:${sessionId}`); the widget generates a fresh `sessionId` per page load on purpose. Provider/model selection is per-profile (each profile's `.env` picks its `HERMES_PROVIDER`/`HERMES_MODEL`); the Hermes Agents panel can change a profile's AI or discuss mistakes with Hermes itself.

## Known gaps (don't assume these exist)

- **Auth is session-only and not data-scoped.** Login/sessions exist (`packages/client-auth`: a single fixed admin identity in `admin-session.ts`, plus per-client `ClientAccount`/`ClientSession`), and `apps/web/proxy.ts` gates `/dashboard` (admin-only), `/dashboard/{businessId}/*` (admin or a client session matching that businessId), and `/api/admin/**` (any valid session). The residual gap: a logged-in non-admin client session is **not** business-scoped at the API layer — mother-level endpoints (`/api/admin/clients`, `/api/admin/revenue/**`, etc.) accept any valid session because both dashboards share components that pass `businessId` from the frontend. Real server-side per-tenant enforcement would be a larger, deliberate change and hasn't been done. `User`/`Business`/`Membership`/`RefreshToken` are orphaned schema tables from an abandoned early auth attempt — not used by the live auth path.
- **No automatic training pipeline.** Training/improvement happens only through the Hermes Control Room: an admin chats with Hermes itself to steer agent behavior (change the AI/model a profile uses, or review and discuss mistakes Hermes made in real client chats). There is no nightly cron that scans the whole conversation database.

## Working conventions

- **Reuse before building.** Check `packages/` and `apps/web/components/` for an existing service/panel/pattern before writing a new one — this codebase has been through several audit-and-delete passes to remove dead/duplicate code; don't reintroduce it.
- **Single database.** After editing `schema.prisma`: `prisma generate`, then `prisma db push` — it picks up the local Postgres `DATABASE_URL`/`DIRECT_URL` from `.env`. No second environment to keep in sync.
- **Verify before calling it done.** `pnpm --filter web run build` must be clean. For anything UI-visible, use the browser preview tools and actually click through the feature — a clean build proves types, not behavior.
- **Commit locally after every completed change**, without waiting to be asked — this is a standing preference from the project owner, not a one-off approval. **Do not `git push` to GitHub**: the owner keeps the remote in sync manually; pushing creates conflict with their force-pushed flows. Use descriptive commit messages explaining *why*, not a changelog of file names.
- **No unrequested abstractions.** Don't add interfaces with one implementation, config for values that never change, or speculative extensibility. Match the size of the change to what was actually asked.
- **Every tabular panel or view gets a fuzzy search box.** Multi-word, case-insensitive (every typed word must appear somewhere in the row's searchable text). Give the input a unique `name="aiva-search-<panel>"` and `autoComplete="off"` so the browser doesn't autofill it. `NoAutofill` (mounted once in the root layout) keeps **every** input/textarea in AIVA read-only until focused, because Chrome otherwise fills fields — search boxes included — with the saved login username; the sign-in form opts out via `data-allow-autofill`. No per-input fix is needed, but never add `autoComplete` values that invite autofill on new inputs. Examples: `RepairsPanel`, `InvoicesPanel`, `DeletedDataPanel`, Reports > Inventory Usage.
- **Windows environment.** Use the PowerShell tool for `robocopy` and other Windows-native operations; Bash tool for everything else. Never pipe em-dashes or curly quotes through `curl -d` in Bash on this machine — they silently corrupt to `U+FFFD`; use a small Node fetch script instead for any non-ASCII payload.

## Data model & feature notes (repairs / revenue / inventory)

- **One number per appointment.** `Business.documentPrefix` (e.g. `PRAZ`) + `Business.documentCounter`; `nextDocumentNumber(businessId)` (`packages/database/src/document-number.ts`) returns `PRAZ00001` (prefix + 5 digits, `INV-` fallback). Assigned in `RepairAppointmentService.book()` as `serialNumber`: appointment # = order # = invoice #. A manual invoice draws from the same counter; numbers are never reused after a delete. One invoice per order.
- **Walk-in bookings.** `WalkInDialog` (Repairs panel button) → `/api/admin/repairs/walk-in` → `RepairController.bookWalkIn`, same booking flow as the website form; technician/priority optional. `RepairAppointment` source shows "Website" or the staff username who entered it.
- **Deleted Data (admin-only).** Every delete through the app calls `archiveDeleted()` (`packages/database/src/deleted-record.ts`) *before* deleting, writing a full JSON copy to `DeletedRecord` (`businessId, entityType, entityId, label, data, deletedBy, deletedAt`). New delete paths must do the same. Not archived on purpose: API keys / channel tokens / password hashes (secrets). The panel is admin-only (`isPlatformAdmin(req)` on the API, hidden from client dashboards).
- **Who did it.** `resolveAdminActor(req)` (`apps/web/lib/admin-actor.ts`) returns the real logged-in username (client accounts) or `ADMIN_USERNAME`; it must **never** yield the literal string `"admin"`. Audit trail: `AuditLog` table + `logAudit()`; UI = `AuditHistoryButton` (click popover).
- **Inventory lots (FIFO cost tracking).** `ProductLot` (`quantity, remaining, costPrice, sellPrice, receivedBy, receivedAt`); helpers in `packages/database/src/inventory-lots.ts` (`consumeStock`, `restoreStock`, `refillProduct`, `reconcileLotsToStock`, `listProductLots`). Selling takes from the oldest lot first and snapshots the weighted lot cost onto the line (`costPrice` + `lotAllocations` on `RepairOrderItem` / `InvoiceItem`), so a later refill at a new cost never rewrites past sales or reports. `Product.stock` (text) stays = sum of remaining; `Product.costPrice/price` = current values (latest refill). Inventory panel: **Refill** (new lot: qty, cost, sell price) and **Lots** (history) buttons per row. Reports read `item.costPrice ?? live product cost` (legacy rows fall back to live cost).
- **Invoice Finalize.** Invoices panel row button (shown when `amountPaid > 0 && balanceDue > 0`): `InvoiceService.finalizeWithDiscount` turns the unpaid gap into `discount`, sets status `paid`, audits `finalized`. The Discount column, print page and emailed PDF all show it.
- **Invoice print / PDF.** Print page (`.../invoice/[invoiceId]/print`) is CSS-fitted to one page when content allows (no browser URL footer: `@page { margin: 0 }`); footer text is "Powered by AIVA" on both the print page and the PDF (`packages/revenue/src/invoice-pdf.ts`).
- **Inventory Usage report.** Reports panel section (`GET /api/admin/reports/inventory`, `ReportingService.getInventoryUsage`): per product line — order/invoice #, qty, who added it, per-unit cost (lot snapshot) vs billed price, discount — with date range + fuzzy search.
- **Uploads.** Logo/chat uploads are persisted in `PERSISTENT_UPLOADS_DIR` (`/opt/aiva/uploads`, survives deploys) and served by `apps/web/app/uploads/[...path]/route.ts`. Turbopack rejects `public/` symlinks that point outside the project root — don't symlink. Build public URLs with `getPublicBaseUrl(req)` (`lib/request-origin.ts`, honours `X-Forwarded-*`); `req.nextUrl.origin` is `localhost:3001` behind the Cloudflare tunnel.
- **Timezones.** Times display in the business's own timezone (`Business.timezone`, GMT-offset labels, deduped in dropdowns); never the browser's.

## Working on the shared VPS

- Other developers push to the same repo and deploy to the same VPS. Don't touch their release folders or deploy state; if something needs to change in their work, flag it to the owner first. Always `git pull --rebase` before pushing.
- **Database changes**: `pg_dump -Fc` to `/opt/aiva/backups/` first. Prefer additive manual SQL over `prisma db push` (it has dropped tables before). Do DB work over SSH `psql` on the VPS, not from a laptop.
- **Test on a VPS staging copy, not prod**: `cp -a "$(readlink -f /opt/aiva/current)" /opt/aiva/staging-test` (**resolve the symlink** — `cp -a /opt/aiva/current …` copies the symlink itself, so the overlay and build then land in the live release and rewrite prod's `.next`), overlay changed files, `prisma generate` + `pnpm --filter web run build`, `next start -p 3002`, drive it with an admin session (credentials in `/opt/aiva/secrets/env.local`). Stop it by PID from `ss -ltnp | grep :3002` (process title is `next-server`, so `pkill -f "start -p 3002"` does not match). Remove all test data afterwards (products, lots, appointments, invoices, `DeletedRecord`/`AuditLog` rows) and reset `documentCounter` if you consumed numbers.
- `deploy.mjs` releases its lock before `pm2 restart`, has subprocess timeouts and removes its own failed worktree. Its own fixes only take effect on the deploy *after* the one that ships them. Its subprocess output isn't logged: run `node scripts/deploy.mjs` in the foreground over SSH to see real errors.
- **Tooling gotchas**: backslashes get eaten by bash heredocs (regexes like `\d`, `\s`) — write such code with the Edit/Write tools. Don't `git add -A` (scratch files such as `cookies.txt`, and untracked skill folders `.agents/`, `.claude/skills/`, `.continue/skills/`, `skills-lock.json`, must not be committed).

## Deployment

**Production runs on a VPS, not Vercel** (`server1.therevenuemakers.com`, domain `app.aiva-ai.net`) — migrated off Vercel/the dev laptop. `pm2` (`ai-chat-web`, `next start -p 3001`) serves the app; a Cloudflare-fronted domain points at it.

- **Deploy pipeline**: manual by design. `.github/workflows/deploy.yml` is `workflow_dispatch`-only (a `ref` input picks the commit to ship) — pushing to `main` does **not** deploy, and the trigger is deliberately gated while engine work is staged locally. A dispatched run POSTs to `/api/webhooks/deploy` with a `DEPLOY_SECRET` bearer token → `scripts/deploy.mjs` on the VPS fast-forwards its own checkout (`/opt/aiva/repo`) to the shipped ref (so a fix to `deploy.mjs` itself actually takes effect on the *next* deploy), does `git worktree add` for the new commit under `/opt/aiva/releases/<sha>`, `pnpm install --frozen-lockfile`, `prisma generate`, `pnpm --filter web run build`, then repoints the `/opt/aiva/current` symlink and runs `pm2 restart ai-chat-web`. Deploy log: `/opt/aiva/ops/deploy.log` on the VPS.
- **The pnpm workspace-symlink flake is fixed, not just retried.** This VPS's pnpm store is shared across every release worktree, so a concurrent `pnpm install` from anywhere else on the box (the untracked-manual-deploy pattern below, in particular) can leave `apps/web/node_modules/@repo/{typescript-config,eslint-config,ui}` partially linked even though `pnpm install` reports success. `deploy.mjs` retries the install once, then — since a workspace-protocol link is always just a plain relative symlink to the package directory, nothing store-dependent — creates any still-missing one directly instead of re-rolling the same race a third time. If a build ever fails on a missing `@repo/*` module again, this is the first place to look.
- **Always verify a deploy actually landed** — `git log --oneline -1` inside `/opt/aiva/current` on the VPS, and `pm2 describe ai-chat-web`'s `exec cwd` should resolve through `/opt/aiva/current`. A "deploy succeeded" log line is not sufficient proof; pm2 does **not** re-read `ecosystem.config.js` or follow a repointed symlink on `pm2 restart` if the process's cwd/script path was frozen at a different location when it was last `pm2 start`'d — this has silently served stale code for a full day in the past.
- **Do not deploy by hand-copying files into a new `/opt/aiva/releases/<timestamp>` folder outside `deploy.mjs`.** A previous manual/AI-assisted deploy did this and left `pm2` pointed at a folder untracked by `git worktree`, which is not compatible with the normal pipeline and caused stale-code incidents. If the site isn't reflecting a pushed commit, check `git worktree list` in `/opt/aiva/repo` on the VPS — the currently-live release should appear there.
- The 30-minute auto-heal cadence is driven by an external scheduler (e.g. GitHub Actions) hitting `/api/cron/auto-heal` with a `CRON_SECRET` bearer token.
